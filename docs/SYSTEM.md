# SYSTEM — BNI Week Slips

## Entities
- `tenants(id uuid, name text unique-ci, home_chapter_name text null, created_at)` — one row per BNI chapter (the tenant). `home_chapter_name` (set in Settings) names the tenant's Home Chapter; when NULL the tenant's own name is used (the `.env` chapter name no longer exists).
- `tenant_members(tenant_id fk tenants, uid text (Firebase), role text default 'admin' check in ('admin','member'), created_at, PK(tenant_id, uid))` — many-to-many user ↔ chapter. **`role` is unused**: roles were removed from the app, so every member of a tenant has full access (import, browse, export, member toggle, chat). The column stays only so roles can be re-applied later. **Open sign-in**: a browser uid with no row here is auto-granted the Home Chapter on first sign-in (`lib/tenant-grant.ts`).
- `chapters(id uuid, name text, tenant_id fk tenants)` — unique per `(lower(name), tenant_id)`; chapter names are per-tenant reference data (import creates Detail chapters inside the importing tenant).
- `members(..., tenant_id fk tenants, is_inactive boolean default false)` — unique per `(tenant_id, lower(name), chapter_id)`. `is_inactive` is the active/inactive flag: **false = active (default for every imported row)**, never rewritten by import.
- `bni_weeks(id uuid, label text unique e.g. "7 January 2026 (Week 2)", meeting_date date unique, week_no int, created_at)` — **shared global meeting calendar** (ISO weeks, no per-tenant content). A tenant only ever sees weeks through its own `import_batches`/slips.
- `slip_referrals(id, tenant_id fk, bni_week_id fk, from_member_id fk null, to_member_id fk null, from_name text, to_name text, other_chapter_member text null, inside_outside text null check Inside/Outside, import_batch_id fk, created_at)`
  - Keep both fk + raw names so other-chapter / deleted members never break display.
- `slip_one_to_ones` — same shape, fields `initiated_by_*`, `met_with_*`, `photo_proof bool default false`, `gains_shared bool default false`.
- `slip_tyfcb(id, tenant_id, bni_week_id fk, member_id fk null, member_name text, amount numeric, other_chapter_member text null, import_batch_id fk)`
- `slip_visitors(id, tenant_id, bni_week_id fk, full_name text, company/email/phone null, invited_by_member_id fk null, invited_by_name text, attending bool default false, ...)`
- `slip_ceus(id, tenant_id, bni_week_id fk, member_id fk null, member_name text, credits numeric, import_batch_id fk, created_at)`
- `import_batches(id, tenant_id, filename, bni_week_id fk null, imported_count, skipped_count, status, error_message, created_at)`
  - `error_message` = JSON `{ errors: string[], skips: string[] }` — one `skips` entry per dropped entry (typing mistakes + already-imported duplicate rows for slips; skipped already-imported cells + ignored cells for PALMS), shown in the Import history dropdown (older rows may be plain text or null).
  - A **multi-week PALMS import stores ONE batch with `bni_week_id = NULL`** (one uploaded file = one batch, cells span weeks); slips batches keep the single week id.
  - `kind` (slips vs PALMS) is **derived, not stored**: `GET /api/import/batches` tags a batch `palms` when its id is referenced by `member_attendance`/`palms_stats`, else `slips`, with a filename fallback (`/palms|chapter_summary/i`) for batches whose rows were deleted individually. The Import screen renders the two kinds as **two separate history tables** (own date/week filters each).
- `member_attendance(id, tenant_id fk, bni_week_id fk, member_name text, present int, absent int, l int, m int, s int, t int, import_batch_id fk null, created_at)` — **PALMS attendance only** (migration 006), unique per `(tenant, week, lower(member_name))`. Written by the new wide-format import as **one cell row per (member, week)** with exactly one flag set to 1 (the letter `P/A/M/S/L` → `present/absent/m/s/l`, `t = 1`); legacy rows from the old single-meeting import may hold counts — a matrix cell renders every set flag as its letter, so both render correctly. The unique index is what makes **skip-duplicates** work: an existing `(member, week)` row is never overwritten. Never derived from slips and never compared against them.
- `palms_stats(...)` — **legacy** (migration 007): the old PALMS-vs-slips comparison totals. Nothing writes or reads it any more (the comparison was removed with the decoupling); the table and old rows remain until cleaned up manually, and "Remove all PALMS data" clears them along with the attendance.
- `chat_sessions(id, tenant_id fk, owner_uid text null, title, created_at, updated_at)`; `chat_messages(id, session_id fk cascade, sender, text, created_at)` — messages inherit tenant through their session.

**Tenant rule:** every tenant-scoped table carries `NOT NULL tenant_id`; every read/write filters `.eq("tenant_id", activeTenant)`; backfill puts all pre-existing rows into the default tenant (created by migration 004).

**Access rule:** there are no roles. Every user who is a member of the active tenant can do everything inside it — import, browse, export, toggle members, chat. The only server-side checks are *authenticated* (`bni_session` cookie) and *member of this tenant* (active cookie validated against `tenant_members`).

**Chat ownership rule:** each chat session belongs to one uid (`owner_uid`, set on create). When the caller has a uid (browser, or service caller with `x-user-uid`), every session list/read/rename/delete/clear/create and chat-history persist filters `owner_uid = uid` — users only ever see their own chats. Callers without a uid (plain service key: tests/scripts) are root and see all sessions of the tenant. Sessions created before migration 005 are backfilled to the tenant's earliest membership.

Name matching: case-insensitive trim, one member row per (tenant, name, chapter) — the same name may belong to several chapters and rows are never merged or moved across chapters. Chapter rule: a BOLD name belongs to its Detail chapter (created in the tenant if missing); every other name belongs to HOME = the tenant's `home_chapter_name` if set, else the tenant's own name. The row for the wanted chapter is reused when it exists, created otherwise. Detail is also stored as text on the slip. Visitor full names never create members (only a non-bold inviter does). Exceptions: a TYFCB's thanked member and every CEU attendee always file HOME regardless of bold.

## Auth / tenant resolution
- **Session cookie**: after sign-in the client POSTs the Firebase ID token to `POST /api/auth/session` → server verifies it (jose + project JWKS, `verifyFirebaseIdToken`) → sets HttpOnly cookie `bni_session` (the verified ID token, ~1h; AppShell re-posts it on every app load so it never goes stale while the tab is open). `DELETE /api/auth/session` clears it (logout).
- **Active tenant cookie**: `bni_tenant` (uuid), set only by `POST /api/tenant { tenantId }` after a membership check, cleared on logout.
- **Server helper** `getTenantContext()` (`lib/server-auth.ts`): reads both cookies → verifies token → `uid` → looks up `tenant_members` for the active tenant → `{ uid, tenantId } | { uid, noAccess: true } | null`. **Open sign-in**: a browser uid with zero memberships is auto-granted the **Home Chapter** by `grantHomeChapter()` (`lib/tenant-grant.ts`, idempotent upsert on the default tenant) before the context is returned, so a first-time Google sign-in lands straight on the data — no SQL. Server-to-server callers (e2e tests, scripts) instead send `Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY` and pick the tenant with `x-user-uid` header or `?tenant=` (default tenant otherwise) — pages accept the same header via Next's `headers()`. A service caller may add `x-user-uid` to **simulate that user** (their membership is looked up for chat ownership; no membership → `noAccess` — service callers are **never** auto-granted, so scripts/tests can still detect a missing membership); without it the caller is root: `uid: null`.
- **Gates**: none beyond auth + membership — `adminOnly()` and the role returned by `requirePageTenant()` were removed with roles. `requirePageTenant()` returns `{ uid, tenantId } | { uid, noAccess }`.
- **Enforcement on every server surface** (all 9 pages + all data APIs):
  - `null` → API returns **401**; page calls `redirect("/login")`.
  - `{ noAccess: true }` → the **no-access screen** with the uid + the exact `insert into tenant_members …` SQL. On the browser path this only happens when the auto-grant failed (Home Chapter row missing); a service caller with `x-user-uid` gets it for any uid with no membership (never auto-granted).
  - Active cookie missing/not a membership → fall back to the first membership (no cookie needed); `POST /api/tenant` to switch explicitly.
- **Client**: AppShell keeps the session cookie fresh, and the nav renders a **chapter switcher** (tenant name ▾) when the user has ≥1 memberships; picking one calls `POST /api/tenant`, then reloads so every server render re-scopes. `GET /api/tenant` returns the active tenant + the switchable list; every nav link (including Import) renders for every user. The nav lists Home · Import · Bni Member · **Slips** · **Slip Report** (`/report`) · PALMS Report · Chat — the **Slips** item is a dropdown holding the five slip list screens (One to One → `/one-to-ones`, Referral → `/referrals`, Visitors → `/visitors`, TYFCB → `/tyfcb`, CEU → `/ceus`; the five formerly flat pills are gone). The dropdown menu is hover/click-open, portaled to `<body>` as a fixed-position panel on desktop (the pill row scrolls, so an absolute child would clip) and an accordion row inside the phone drawer.

## Actions / APIs
- `POST /api/auth/session { idToken }` → verifies + sets `bni_session`; `DELETE /api/auth/session` clears cookies.
- `GET /api/tenant` → `{ tenant: {id, name} | null, tenants: [{id, name}], noAccess: bool, uid }` (no role field any more).
- `POST /api/tenant { tenantId }` → 200 (membership validated, cookie set) or 403 if the uid is not a member.
- `POST /api/import/report` (multipart: `file` only — the week comes from the file's title row) — **requires tenant only** (any member of the active tenant may import); batches/slips/members/chapters created with `tenant_id` = active tenant. Slips and PALMS are independent: the response never mentions PALMS.
  1. Validate ext `.xls/.xlsx/.csv`, size < 10MB.
  2. Parse via `xlsx` (`lib/report-import.ts: parseReportFile`): header row must contain From/To/Slip Type (others optional).
  3. Upsert `bni_weeks` by label (global); create `import_batches` row (tenant-scoped).
  4. Classify all rows in memory, preload members/chapters of THIS tenant (1 select) + bulk-insert the missing (1 insert), then drop payload rows whose signature (file-derived identity fields, `lib/import-dedup.ts`) already exists among this tenant's slips **for the same week** — a re-import skips them (per-row `skips` entry + one aggregated error line) — and bulk-insert the rest. Within one file every entry is kept, even identical ones (~12 HTTP calls total).
  5. Update batch counts, invalidate the chat snapshot cache, return JSON.
- `POST /api/import/palms/preview` (multipart: `file` — `.xls/.xlsx`) — **requires tenant only**; dry-run of the wide PALMS file. Parses it (`lib/palms-import.ts: parsePalmsWideFile`), resolves every date column to the tenant's Wednesday calendar and returns `{ filename, from, to, memberCount, weeksMatched, weeksUnknown[], cellTotal, cellNew, cellSkipped, skippedSamples[], issues[], errors[] }`: `cellNew`/`cellSkipped` come from checking each parsed `(member, week)` against existing `member_attendance` rows, `skippedSamples` lists up to 10 `"Name — dd MMM"` entries that already exist, `weeksUnknown` lists header dates not on the calendar (their cells are skipped with a warning, never a hard error), `issues` lists cells whose value is not a known letter. Errors (no header row, no readable date columns — e.g. the old single-meeting format) → 400.
- `POST /api/import/palms` (multipart: `file` — `.xls/.xlsx`) — **requires tenant only**; commits the same file (re-parsed, client re-uploads after the preview, mirroring the slips flow).
  1. Parse + resolve columns exactly as the preview (same errors → 400).
  2. Load existing `member_attendance` for (tenant, matched weeks) and **filter to cells that do not exist yet** — an existing `(member, week)` row is skipped, never replaced (the unique index `member_attendance_week_member_uq` enforces it; a concurrent duplicate surfaces as 23505 and is counted as skipped).
  3. Create **one `import_batches` row per uploaded file** (`bni_week_id = NULL` — a file spans up to ~27 weeks), insert the new cell rows in chunks of 500 (row-by-row fallback), then store counts: `imported_count` = inserted cells, `skipped_count` = already-imported cells, `error_message = { errors: issues, skips: skippedSamples }`. No caches are invalidated (attendance touches only `/palms`; batches carry no week id, so week options/latest-week are unchanged). Returns `{ importedCount, skippedCount, memberCount, weekCount, weeksUnknown[], issues[] }`. Zero new cells → nothing is created (the panel already hides the Import button in that state).
- `DELETE /api/import/palms` — **requires tenant only**; 404 when the tenant has no PALMS attendance. Removes **all** PALMS data for the tenant: every `member_attendance` row, the `palms_stats` rows, and the batches those attendance rows reference — slips batches/rows are never touched (they are never referenced by attendance). Called by the **Remove all PALMS data** action in `PalmsImportPanel` on `/palms`. Per-file removal stays on `DELETE /api/import/batches/{id}` (deletes exactly that batch's cells).
- `DELETE /api/import/batches/{id}` — **requires tenant only**; unknown/other-tenant id → 404. Deletes the `import_batches` row **and every row carrying `import_batch_id = id`**: the batch's rows across the 5 slip tables and — when the batch is a PALMS import — its `member_attendance` rows plus the `palms_stats` row it stored. Other batches, weeks and imports are untouched (slips of the same week stay; a superseded PALMS import has no rows left and only its history entry goes). Invalidates the same caches as a fresh import (week options, distinct filter options, latest-imported-week, chat snapshot) and returns `{ ok: true, removed: {…counts} }`. Wired to the per-row **Delete** button (confirm dialog) in the Import screen's history table (`components/ImportPage.tsx`).
- PALMS-vs-slips comparison — **removed**: `lib/palms-compare.ts` is gone, `palms_stats` is no longer written, and no screen or banner ever shows PALMS numbers next to slip numbers (the two reports are independent).
- `GET /api/palms/export?week=&format=xlsx|csv|pdf|json` — **requires tenant**; `week` accepts the same scope as the report (one id, comma-separated list, `all`). Produces the `/palms` matrix: a `PALMS Report` block (title + member count + `Member | dd MMM | dd MMM | …` rows — **cells identical to the screen**: the imported letters, blank for cells never imported) and nothing else. `format=json` returns the same content for the in-browser PDF (same reason as the report: generated PDF bytes get swallowed between server and browser); the server PDF prints the title once followed directly by the styled table.
- Missing meeting files (`lib/data-health.ts`): `missingWednesdays(importedDates, todayIso)` — pure function; every Wednesday from the tenant's first imported meeting date up to today that has no imported slips file is "missing". `fetchMissingMeetingFiles(tenantId)` feeds the warning banner (dates, capped display).
- `GET /api/weeks` → weeks **the tenant has imported** (via its `import_batches`), drives the list/report week filters (the import screen derives its week from the uploaded file's title row, not from this API).
- `GET /api/<resource>?week=&q=&page=&pageSize=` for each of members/referrals/one-to-ones/visitors/tyfcb/ceus → `{ rows, total }` read-only, all `.eq("tenant_id", …)` (column filter options/distinct values too).
- Active/inactive members: `PATCH /api/members/{id} { isInactive: boolean }` → **requires tenant only** (any member may toggle), updates `members.is_inactive` for a row of the active tenant only (`.eq("tenant_id", …)` + `.eq("id", …)`), returns the updated row `{ id, is_inactive }`; unknown id / other tenant → 404. `GET /api/members` and the `/members` page return **inactive rows to everyone** (no role filter), so the toggle and the rows are visible to every user. The `/members` table renders the `Active` column **before Name** with a checkbox toggle (`components/MemberActiveToggle.tsx`, optimistic + `router.refresh()`); `SlipsTable` renders the `active` column through it. Flag flips never delete data — slips/exports/chat are untouched. A successful PATCH calls `clearDistinctCache()` (`lib/distinct.ts`), otherwise the 5-minute cached dropdown options would still offer the newly inactive member. The `/members` page also computes **active/inactive counts** (two unfiltered head-count queries) and accepts **`?active=1`** to list only active rows; `components/ListShell.tsx` renders the counts as a sub line under the title and an **Active** checkbox inside the table's Active header cell (opt-in — without it the default list still shows everyone, so existing totals are unchanged).
- Report (`/report`, export via `GET /api/report/export?week=&tab=&format=`): sections/tabs One-to-One, Referral, TYFCB, Visitor, CEU. `week` accepts one id, a **comma-separated list of ids** (the week box is a **single-select** — the screen scopes to one meeting, its **✕** clears it to `week=all`, while exports and API callers may still pass comma-separated id lists and multi-week exports gain a BNI Week column), or `all`. Each section table's own **BNI Week header cell** (`w_<section>`) overrides the global scope per table (single-select in the UI, the param still accepts comma lists); an overridden export is marked `-mixed` and the overridden sheet gains the BNI Week column. From/To name filters stay multi-select; the **Other Member's Chapter** (`detail`) filter is single-select. One-to-One stat cards/badge/grand total (home card + chat total too) use the owner count — a bold (other-chapter) side counts 1, both-home counts 2; lists/exports stay one row per slip. The CEU stat card shows **distinct members** with slips alongside the credits (`12 Members · 87 CEU credits`, `1 Member · …` for one) via `SectionData.cardStat` (card **and the export Summary** show it — section badge, export tables and footer sums keep the per-slip numbers). The Referral stat card shows the **given** count only (from = home member, `RGI + RGO` = 54 for Week 40; `cardCount`) with the four PALMS chips `RGI · RGO · RRI · RRO` in the badge line (received `RRI/RRO` is never part of the headline; section badge/table keep the row count, while the export Summary row mirrors the card's given count + chips). Present/Absent (`P/A/L/M/S`) are meeting-attendance facts that exist only in BNI's PALMS report — they are not derivable from the 7-column slips import; they reach the app through the PALMS import below. Every export (xlsx/csv/pdf, including the in-browser PDF) opens with a **Summary**: week + filters, one row per section carrying exactly what the stat card shows (`count = cardCount ?? metricCount`, `info = cardStat ?? stat ?? totalLabel` — Referral is the given count plus the RGI/RGO/RRI/RRO chips, CEU the `12 Members · 87 CEU credits` line) — no grand total row in csv/xlsx/pdf (only the JSON format keeps `summary.total`); in the PDF each section prints its title once followed directly by the styled table (whose header repeats on every page) — there is **no duplicated plain-text column-header row**; TYFCB and CEU sections keep their **Total footer rows** in every format and on screen. The page head carries **no PALMS panel** — the two-step upload (`components/PalmsImportPanel.tsx`: choose file, then press **Import**; selecting a file never starts an import by itself) lives on `/palms` and `/import` only. The xlsx export is built with **ExcelJS** so the From/To cells of bold (other-chapter) names print **bold exactly like the screen and the PDF** (CSV has no formatting). All section queries, batch lists, stat cards and export cells are scoped to the active tenant.
- PALMS Report (`/palms`): member × week matrix — `Member | dd MMM | dd MMM | …`, one column per meeting week that has attendance (ascending `meeting_date`), cells the imported `P/A/M/S/L` letters (colour-coded per letter), blank when a cell was never imported. Week box = single-select + All weeks (**default scope = all weeks**); its options come from **weeks with attendance** (a dedicated PALMS week-options query — not the slips-derived `GET /api/weeks` list, since a multi-week PALMS batch stores no week id). `lib/palms-view.ts: fetchPalmsMatrix(tenantId, weekIds)` reads `member_attendance` (paged) and derives each cell's letters from its flags (legacy count rows render every set flag as a letter); `fetchPalmsWeekOptions` builds the filter options; `fetchPalmsImportRecord` returns the latest PALMS batch (filename + date) for the panel's "Imported …" line. The screen renders the PALMS upload panel (`components/PalmsImportPanel.tsx` — two-step preview flow against `/api/import/palms/preview` + `/api/import/palms`, Remove-all action when data exists), the matrix table, and the export switch (`components/PalmsExportButtons.tsx`) wired to `GET /api/palms/export` — column labels/cells come from `lib/palms-view.ts` so screen and files never drift. The page has **no data-health banners** (PALMS says nothing about slips). Below the matrix the page renders the **26-week attendance breakdown** card — title **Last 6 Months rolling period (26 weeks): Active members** — independent of the week box: `lib/palms-view.ts: fetchPalmsAttendanceStats(tenantId, todayIso)` resolves the Wednesday meetings inside the rolling window (`lib/palms-buckets.ts: rollingWindow` — `today − 181 days … today`, a 182-day = 26-week span, so future meetings never count), sums each member's `absent` / `m` / `s` flags over those weeks, drops names marked inactive in `members` (case-insensitive name match; a name with no member row counts as active) and buckets them per letter with the pure `bucketAttendance(rows, inactiveKeys)`: **3+ / 2 / 1** buckets (mutually exclusive per letter, the three letters independent), labels `3+ Absents … 1 Absent`, `3+ Medicals … 1 Medical`, `3+ Substitutes … 1 Substitute`, each with its count and the names alphabetically. The card renders only when at least one A/M/S letter exists in the window.
- Data-health warnings (shared `components/DataWarnings.tsx`, rendered on `/report` **only**): (1) missing Wednesday slip files (`lib/data-health.ts`) — amber banner listing the dates; (2) **not imported yet** (`lib/data-health.ts: fetchUnimportedData`) — red banner listing each week **in scope whose slips file is missing**, honouring the page's week scope. PALMS never appears in either banner and `/palms` renders none. **Warnings only: when everything is imported the component renders nothing** (no success/green line). Nothing blocks an import.
- Loading skeletons: `/import`, `/palms` and `/report` have route `loading.tsx` files rendering the geometry-accurate `ImportSkeleton` / `PalmsSkeleton` / `ReportSkeleton` from `components/Skeletons.tsx` (same pattern as the list pages), so navigation shows the real layout immediately. `PalmsSkeleton` mirrors the PALMS Report head (export switch), the panel (`PanelSkeleton title="PALMS Report (6 months)"`), the controls row and the matrix card.
- Chat (`POST /api/chat/generate` `{ message, history? }` → `{ text }`): **requires tenant** — sessions list/create/switch, message history and chat persistence are tenant-scoped **and owner-scoped** (`owner_uid = caller uid` when the caller has one; plain service callers see/write all sessions of the tenant), and the snapshot is built and cached **per tenant** (90s TTL, key includes `tenant_id`; any import invalidates the cache). Gemini answers from a cached snapshot of that tenant's slips (`lib/chat/snapshot.ts` — chapter totals, per-week `weekly[]`, all-time `members[]`, plus a member × week query index; cleared on every import via `clearSlipsSnapshotCache`). Scoped and member-level questions (per meeting/month/date-range/latest-week "who did X", top-N rankings, unique member counts, inside/outside splits) are answered through the **`chapter_query` function-calling tool** (`lib/chat/query-index.ts`: scope kind week|month|range|latest|all + metrics + members filter + orderBy + topN → per-member rows with scope hint when nothing matched) — the chat NEVER replies that such data is unavailable; an unknown date gets "no such meeting" plus the available weeks. Whole-chapter weekly totals and all-time facts come from the snapshot itself. Model fallback chain; up to 3 tool rounds per question, echoing each model functionCall part verbatim (thoughtSignature). **Output budget (measured)**: `generationConfig` = `maxOutputTokens 4096` + `thinkingConfig.thinkingBudget 512` — thinking tokens share the output budget, and the original `2048` let reasoning spend ~1970 tokens, cutting the answer mid-list (`finishReason MAX_TOKENS`): the model then promised N names and delivered far fewer, and on the next turn invented a "display truncation" excuse. At `4096` alone a production-sized prompt (~20k tokens) ran ~11.4s; capping thinking to 512 brings it to ~5s, so each attempt fits `MODEL_ATTEMPT_TIMEOUT_MS` (20s, ×3 fallbacks = the route's `maxDuration = 60`). If a reply still arrives with `MAX_TOKENS`, the text is returned with an explicit "cut short by the length limit — it is incomplete" notice appended so a partial list is never read as the whole answer. Attachments: up to 3 files (4MB each, 8MB total) — png/jpg/webp/gif/pdf go to Gemini as inlineData parts; xls/xlsx/csv are converted to capped text server-side (`lib/chat/attachment-text.ts`) so a weekly report can be uploaded and questioned; file names persist as `[attached: …]` markers in `chat_messages.text` (split back into chips on history load). Every message has a ··· menu — a vertical kebab (⋮), hover-revealed at the container's top corner (user message = top-left, AI message = top-right), never with a background box: Copy, Select all, Tag. Tag opens a bar above the composer labelled "Tagged your message" / "Tagged Slips AI response" (× to cancel); the tagged text is sent as per-turn `replyTo` context appended to the Gemini prompt and persists as a hidden `[tagged: …]` marker in `chat_messages.text` (split off on history load, so visible text stays clean and the title never starts with a marker). The sent query shows a "Tagged" chip above its text; clicking it scrolls the chat log to the tagged message and briefly flashes it (nearest preceding match on the tagged text, so it works after reload too). All chat-box text (textarea, buttons) uses the app font. **Suggested questions follow the conversation**: the model is instructed to end its reply with a trailing `SUGGESTIONS:` block of 4 follow-up questions grounded in that turn; `askGemini` parses the block out of the answer (line must end with `?`, `]`/`|`/newlines stripped, max 5 kept) and returns it as `GeminiResult.suggestions`, so the visible answer never shows it. The route appends a hidden `[suggestions: q1 | q2 | q3]` marker to the AI row in `chat_messages` (split off on history load exactly like `[tagged:]`/`[attached:]`, never sent back in `history`) and returns `suggestions` alongside `text`. The chips under the composer render the newest AI message that carries suggestions; a chat with none (new chat, older history, or a model that omitted the block) falls back to the 5 static starter questions. **Share to WhatsApp** (no endpoint, no server round-trip): `lib/whatsapp.ts` → `whatsappShareUrl(text)` = `https://wa.me/?text=<encodeURIComponent(text)>`; the toolbar's **Share chat** shares `buildChatShare(messages, title)` → `{ text, total, included }` — session title header, `You:` / `Slips AI:` per turn, attachment names as `[file: …]`, the greeting line excluded. `SHARE_MAX_CHARS` is **20 000** (the earlier 6 000 silently cut a normal long chat in half, which read as "the share lost the conversation"); only a transcript past the budget drops turns, oldest first, behind an explicit "(Earlier messages omitted)" lead-in, and a single oversized turn is kept whole rather than cut. While `included < total` the toolbar shows `Share chat will send the newest N of M messages` next to the message count (and says the same in the button's tooltip), so the member knows **before** sharing instead of finding a note at the top of the message. The message ⋮ menu's **Share to WhatsApp** shares that message's text only. Both call `window.open(url, "_blank", "noopener,noreferrer")` from the click handler, so the recipient picker is WhatsApp's — the app posts nothing and stores nothing new.
- Weeks: chapter meets every **Wednesday** (`lib/weeks.ts`). ## Validation / errors
- Missing headers → 400. Unknown slip type / empty both From+To → skip + collect in `errors[]` (max 50 returned).
- A signed-in user who is not a member of the requested tenant → 403. Cross-owner chat reads/renames/deletes → 404 (`Chat not found.`).
- Duplicate slip (same week + same from/to/amount/detail) **within one file** → imported too; `supabase/migrations/003_allow_duplicate_slips.sql` drops the per-week unique indexes so no row is ever skipped for being a duplicate. A **re-import** of rows that already exist for the same tenant + week → skipped (`lib/import-dedup.ts` builds one signature per slip table from the file-derived fields — names, chapter/flags, amount/credits, inside/outside — and matches it against the existing rows of that week only).
- Every skipped entry stores a reason in the batch's `skips` log (cap 1000) — shown per batch in the Import history dropdown. The Import screen lists history in **two tables** — Slips Audit Report imports and PALMS Report imports (batch `kind` from `GET /api/import/batches`). For slips, typing mistakes are the ONLY pause (the preview returns `rowIssues` and the UI asks for permission before importing); the PALMS preview instead reports **which cells are already imported and will be skipped** (counts + samples) before the user presses Import.
